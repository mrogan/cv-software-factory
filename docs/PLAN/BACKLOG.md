# Backlog

Follow-ups and ideas that have no milestone yet, or need more thought before they get one. It is a holding place, not a plan: when a milestone starts, take what fits into its file and delete it here; when one ends, add what it left open.

Decisions that need Martin go in [`OPEN-QUESTIONS.md`](../OPEN-QUESTIONS.md) instead. Things that are simply true go in the spec, `COMPONENTS.md` or `AGENTS.md`.

| Item | Why it matters | Likely home |
|---|---|---|
| Updates for what Dependabot can't see | `mise.toml`, the chart versions in the Argo CD Applications, the Argo CD chart in the `Makefile` and the k3s image are pinned by hand and will drift. Renovate covers all of them; a scheduled check is the smaller option. | Before milestone 6 |
| The seeded baseline and improvements | Reset restores the tree the private repository published. Once the factory ships an improvement to the app, that tree is out of date, and a reset would undo the improvement. Either the baseline moves with each improvement or reset re-applies the patches to the current app. | Milestone 8 |
| The app's repository can claim any ingress host | Its Argo CD project allows an Ingress in the `website` namespace, and an Ingress names its own host: a change there could claim `console.localhost` and take the console's traffic. Admission control should allow it only the app's own host. | Milestone 6, with Kyverno |
| The correct app goes stale | The private repository keeps the app as first written; the public one moves on. A patch written against the old app may not apply to the new one, and the private CI only proves it against the old. The injector needs patches that apply to the app as it stands. | Milestone 9 |
| Two versions side by side | Every signal carries the version and the dashboard splits by it, but nothing has yet run two versions at once to show it. | Milestone 6 |
| Tempo answers a minute or two late | A new trace is not queryable straight away in Tempo 3. Verify and the replay's captured artifacts must wait for it, or rely on metrics and logs for anything immediate. | Milestone 6 |
| The console reads every event | The page fetches the whole history on load: 520 sample events are about 30 KB gzipped, well inside the speed budget. A real factory will outgrow that; then the server sends a snapshot of the projection and the events since, or pages the reel. | When the event count passes about 5,000 |
| The app's metrics name a path, not a route | `http_route` holds `/products/glove-left`, not `/products/:slug`, so each product is its own series and a rule's minimum request count is met by none of them while the shop's traffic is thin. The log watcher still sees the errors, and the intake names the route by what the log says. The objectives would judge a route properly with a template on the metric, or a recording rule that groups by the log's route. | Milestone 6, with the traffic generator |
| The factory's volumes are one node's | The artifacts and cassettes volumes are ReadWriteOnce, shared by several pods because k3d has one node. A cluster with more nodes needs a volume many pods can write, or object storage. | Milestone 7, with DigitalOcean |
| A route ticket beside a ticket for every page | A ticket for `*` absorbs later signals of its class on one route, but tickets already open on single routes stay open beside it. If a class turns out to be everywhere after the probes have reported it on a few routes, the same defect has several tickets. | When the count shows it |
| A route's parameter has more than one name | The factory names a route's parameter by what it holds (`/departments/:department`), and the answer key may use another (`:slug`). The count compares templates exactly, so the same fault on the same route can match nothing. Comparing templates with their parameters' names left out would settle it. | Before the scoreboard (milestone 6) |
| Screenshots on pull requests | The line holds a screenshot for each work item, and a reader of a pull request would see the defect being fixed. GitHub shows an image only from a URL it can fetch, and has no API for attaching one to a description or a comment; the local console is not reachable from github.com. The replay site or the hosted console serves the work item's public screenshots, and the description links them. | Milestone 7 or 10 |
| Acceptance criteria without a tagged test | Test integrity should fail a fix whose spec has a criterion no test names. The spec lives in the event store, which GitHub's checks cannot reach, and a criterion copied into the pull request would be the agent's word for it. The check needs the spec from somewhere the coder cannot write. | Milestone 6 |
| Prompt caching for agents' calls | Nothing in the factory sets up Anthropic's prompt cache: the gateway passes a runner's `cache_control` markers through untouched, and whatever caching happens is what the Agent SDK does on its own. It does cache: the first smoke run in the cluster read 23,251 tokens from the cache and wrote 8,739, against 8 of fresh input, over 4 calls. Nobody has measured whether placing breakpoints ourselves (the spec, the repository's `AGENTS.md`, a resumed session) would change what a fix costs; a cache write costs more than fresh input, so it may not. `model_calls` already records cache reads and writes per call. | Milestone 5, with the cost measurement (task 15) |
| Model access with no key on `do` | Anthropic accepts short-lived tokens from an identity provider it trusts, in place of an API key. The local cluster has no public issuer to trust, so `local` keeps a key. If DigitalOcean's Kubernetes publishes its service accounts' issuer, the gateway on `do` could hold no key at all, as `aws` holds none through Bedrock. | Milestone 10 |
| Internal APIs trust the network alone | The GitHub worker's actions, the line's step API and the gateway's routes for workers take any caller that can reach their port. A NetworkPolicy is all that stands in the way, and nothing does when a worker runs on the host. A secret per caller, or mTLS, would make one wrong policy cost less. | Before the cluster leaves the laptop (milestone 10) |
| A threat model for runners | The fence is tested, but nothing says which ways out are known and accepted. Closed: DNS from agent pods (no resolver), the gateway's server tools (refused). Open: the job token in the Job's spec, readable by anyone who can read Jobs in `runners`; whatever an agent writes into a model call or its handback, which the gateway and the line pass on. Writing them down says which are accepted, which are to close, and what `make egress` must prove. | Milestone 9, with the red team |
| Installation tokens narrowed by permission | The worker narrows each installation token to one repository, but it carries all the App's permissions. Asking for only what each action needs (contents, pull requests, checks, issues) limits what a bug or a stolen token can do. | Milestone 6 |
| The worker's actions are written out three times | Each action is declared in the `Actions` interface, in `ARGS` (its Zod schema) and in `CALLS` (its dispatch), by hand, and they can drift (`REVIEWERS.md`, rule 1). One table per action, holding its schema and its handler, would give the dry run, the live worker and the HTTP layer one source. Nothing tests the wiring in `service.ts` and `commands/github.ts` at their seam either. | When the next action is added |
| Cassettes hold whole prompts and tool output | A recording of an agent's call holds source, issue text and tool results. Nothing limits how long recordings are kept, and nothing stops one in `/tmp/cassettes` being committed. The key's date rewrite also changes a "Today's date is" inside a tool result, so two requests that differ only there share a key. | Milestone 6 |
| The Agent SDK against the gateway | The gateway lets through only the betas and fields today's Agent SDK sends. No test runs the real SDK against `/v1/messages`, so an update that sends a new beta would pass CI and be refused in the cluster. A test that runs the SDK against the gateway, replaying from a cassette, would catch it in the update's own pull request. | Before the Agent SDK is next updated |
| Job tokens never expire | A job's token ends when its step ends (`packages/store/src/job-tokens.ts`). If the line crashes mid-step, the token stays good until the line runs that step again; only the Job's own deadline bounds what the agent can do with it. An expiry on the token, a little past the deadline, would close that. | Milestone 9, with the threat model for runners |
| Runner Jobs outlive a line that restarts | A line that crashes or restarts forgets the steps it had in hand, and their Jobs run on to their deadline, spending model calls nobody will read. The line could delete the `runners` Jobs it holds no step for as it starts. A cost leak, not a correctness one: the step runs again as a new job. | Milestone 5, before the soak (task 15) |
| `updateBranch` is outside the branch guard | The GitHub worker refuses to move, delete or commit to a branch the factory does not own, but `updateBranch` (merging main into a pull request's branch) does not ask (`github/actions.ts`). Only the factory's own code calls it today, on its own pull requests. | When something outside the factory calls it |
| release-please writes outside the branch guard | The release worker lets the release-please library write its own branch, so the guard never sees it (`github/releases.ts`). It is a known exception; `COMPONENTS.md` should say so beside the guard. | Milestone 6 |
| The runner's git ignores the prepare step's environment | `git()` and `gitWith()` in `apps/runner/src/git.ts` build their own environment, so a setting `prepare` passes is lost. Nothing relies on one yet. | When a step needs one |
| `**/` matches any prefix | In a scope or a code-owned pattern, `**/AGENTS.md` matches `src/NOTAGENTS.md` too (`github/paths.ts`): it should match only at a path's start or after a `/`. It errs towards refusing a change, so it is safe, but wrong. | When the fence is next changed |
| CODEOWNERS is read loosely | `ownedPaths` takes each line's pattern, but not as GitHub does: anchoring, lines with no owner, and escaped `#` are not handled. The repositories' CODEOWNERS files use none of these today. | When a CODEOWNERS file uses one |
| Binary, rename and mode-change patches fail the step | A coder's change the factory cannot read (`github/patches.ts`) counts as a failed step, run again blind, rather than going back to the coder with the reason, as a change outside its scope holds. Rare, and the coder's prompt asks for neither. | Milestone 5, with the coder (task 11) |
| The step API cannot ask for a result or a seed | `POST /v1/steps` (`runners/serve.ts`) takes a commit, a prompt, a skill and bounds, but not `base`, `result`, `resultFiles` or `seed`, so it cannot try an agent's structured result by hand. The agent bench covers the need. | When the bench does not |
| `gates.finished` counts two different things | Its `passed` counts every check that passed, while `failed` names only the required checks that failed (`line/gates.ts`). Readers refold `gate.finished` today, so nothing is wrong yet; a reader that trusts the counts would be. | Before a reader uses the counts |
| No answer is recorded when Martin merges | A merge ends the work item, but no `hold.answered` closes the hold that waited for it, so a reader of the hold alone sees it open. The console clears it itself. | When another reader needs it |
| Some writes are reconciled only by their record | A handback's writes are recorded as they begin and when they are done, and a push or a pull request begun and not recorded is made safe to do again. Two are not: an issue opened just before a crash, before its number is recorded, is opened again; and a review posted just before one is posted twice (its check run, made first, may be made twice too, which is harmless: GitHub shows the latest). Looking first needs a read of the factory's issues and of a pull request's reviews. | Milestone 5, before the soak (task 15) |
| Closing a work item leaves its pull request open | When Martin rejects a held work item, the line closes it and its issue, but there is no action to close a pull request, so its pull request stays open for Martin to close. | With the next GitHub worker action |
| A work item's spend cap never resets | The gateway caps what a work item spends over all of its history (`gateway/spend.ts`). The bench and the smoke run each take a work item of their own per run, so they never meet a cap an earlier run used up, but a real work item that reaches its cap stays there for good: only deleting rows from the audit table frees it. Whether a cap should reset, by round or by Martin's answer to a hold, is a decision of its own. | When a work item first reaches its cap |
| Bench cassettes are one developer's | The bench works in a folder in the developer's own cache, whose path reaches the agent's prompt, so a step recorded by one developer replays only for that developer. Leaving the path out of the key, as the date is, would share them. | If a second developer works on the prompts |
| Pull request templates as guidance | The describer fits a description to its change and reads a repository's pull request template as questions, not headings (`apps/runner/plugin`), but `docs/SPECIFICATION.md` §9 still says "Agent PRs follow a template: problem, evidence, change, tests, risk, rollout", and both repositories' `.github/pull_request_template.md` are headings to fill. All three are code-owned. Proposed for §9: "An agent's pull request description fits its change: the describer writes it from the ticket, the spec, the diff and the review. The template's questions (problem, evidence, change, tests, risk, rollout) are what a reviewer should be able to answer from it, not headings to fill." Proposed for each template, as one HTML comment: the title is a Conventional Commit, which becomes the squash commit (the factory's example `fix(console): keep the scrubber inside the panel`, the app's `fix(search): match the whole phrase`); describe the change at the length it needs, a line for a small change, a diagram for one with a shape worth seeing; between them, the title and description should let a reviewer answer Problem (what is wrong or missing, and for whom? Link the issue), Evidence (how do we know? Trace IDs, log lines, screenshots, a failing check), Change (what does this do?), Tests (what proves it, and how were they run?), Risk (what could go wrong, and what does it touch: workflows, `deploy/`, dependencies, policy? "Low" is an answer) and Rollout (how does it reach the cluster, and how is it undone?); these are questions, not headings to fill: leave out what a change does not raise. | Waiting for Martin |
