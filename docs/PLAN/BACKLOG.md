# Backlog

Follow-ups and ideas that have no milestone yet, or need more thought before they get one. It is a holding place, not a plan: when a milestone starts, take what fits into its file and delete it here; when one ends, add what it left open.

Decisions that need Martin go in [`OPEN-QUESTIONS.md`](../OPEN-QUESTIONS.md) instead. Things that are simply true go in the spec, `COMPONENTS.md` or `AGENTS.md`.

| Item | Why it matters | Likely home |
|---|---|---|
| Updates for what Dependabot can't see | `mise.toml`, the chart versions in the Argo CD Applications, the Argo CD chart in the `Makefile` and the k3s image are pinned by hand and will drift. Renovate covers all of them; a scheduled check is the smaller option. | Before milestone 6 |
| The seeded baseline and improvements | Reset restores the tree the private repository published. Once the factory ships an improvement to the app, that tree is out of date, and a reset would undo the improvement. Either the baseline moves with each improvement or reset re-applies the patches to the current app. | Milestone 8 |
| The app's repository can claim any ingress host | Its Argo CD project allows an Ingress in the `website` namespace, and an Ingress names its own host: a change there could claim `console.localhost` and take the console's traffic. Admission control should allow it only the app's own host. | Milestone 6, with Kyverno |
| The correct app goes stale | The private repository keeps the app as first written; the public one moves on. A patch written against the old app may not apply to the new one, and the private CI only proves it against the old. The injector needs patches that apply to the app as it stands. | Milestone 9 |
| Two versions side by side | Every signal carries the version and the dashboard splits by it, but nothing has yet run two versions at once to show it. | Milestone 6 |
| Tempo answers a minute or two late | A new trace is not queryable straight away in Tempo 3. Verify and the replay's captured artifacts must wait for it, or rely on metrics and logs for anything immediate. | Milestone 6 |
| The console reads every event | The page fetches the whole history on load: 430 sample events are about 25 KB gzipped, well inside the speed budget. A real factory will outgrow that; then the server sends a snapshot of the projection and the events since, or pages the reel. | When the event count passes about 5,000 |
| The app's metrics name a path, not a route | `http_route` holds `/products/glove-left`, not `/products/:slug`, so each product is its own series and a rule's minimum request count is met by none of them while the shop's traffic is thin. The log watcher still sees the errors, and the intake names the route by what the log says. The objectives would judge a route properly with a template on the metric, or a recording rule that groups by the log's route. | Milestone 6, with the traffic generator |
| The factory's volumes are one node's | The artifacts and cassettes volumes are ReadWriteOnce, shared by several pods because k3d has one node. A cluster with more nodes needs a volume many pods can write, or object storage. | Milestone 7, with DigitalOcean |
| A route ticket beside a ticket for every page | A ticket for `*` absorbs later signals of its class on one route, but tickets already open on single routes stay open beside it. If a class turns out to be everywhere after the probes have reported it on a few routes, the same defect has several tickets. | When the count shows it |
| A route's parameter has more than one name | The factory names a route's parameter by what it holds (`/departments/:department`), and the answer key may use another (`:slug`). The count compares templates exactly, so the same fault on the same route can match nothing. Comparing templates with their parameters' names left out would settle it. | Before the scoreboard (milestone 6) |
| Screenshots on pull requests | The line holds a screenshot for each work item, and a reader of a pull request would see the defect being fixed. GitHub shows an image only from a URL it can fetch, and has no API for attaching one to a description or a comment; the local console is not reachable from github.com. The replay site or the hosted console serves the work item's public screenshots, and the description links them. | Milestone 7 or 10 |
| Acceptance criteria without a tagged test | Test integrity should fail a fix whose spec has a criterion no test names. The spec lives in the event store, which GitHub's checks cannot reach, and a criterion copied into the pull request would be the agent's word for it. The check needs the spec from somewhere the coder cannot write. | Milestone 6 |
| Model access with no key on `do` | Anthropic accepts short-lived tokens from an identity provider it trusts, in place of an API key. The local cluster has no public issuer to trust, so `local` keeps a key. If DigitalOcean's Kubernetes publishes its service accounts' issuer, the gateway on `do` could hold no key at all, as `aws` holds none through Bedrock. | Milestone 10 |
