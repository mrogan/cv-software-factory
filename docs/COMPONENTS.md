# Software Factory: components

The parts of the factory, how they connect, and what each one is built with in v1. The specification says *what* the factory must do; this document says *which part does it*. Where they differ, the specification wins.

Each component lists its v1 choice and, where useful, what it might grow into. Later choices are ideas, not commitments.

## Planes

| Plane | Job | Rule |
|---|---|---|
| **GitHub** | Source of truth and deterministic gates | No model judgement decides anything here |
| **Factory** | Where agents think, and the console | The only plane with model access |
| **Runtime** | Runs the app, telemetry and delivery tooling | Pulls from git; nothing pushes to it |
| **Private** | The correct app, defect patches, answer key, injector catalogue, environment settings | Never reachable by agents |

## Factory plane

| Component | Purpose | v1 | Later |
|---|---|---|---|
| **Orchestrator** | Work queue, state, retries, concurrency, stop the line | Postgres-backed queues and TypeScript workers. **The inbox:** senses insert signals, as the line does the planner's findings (each with an id from its work item and what it says, so neither a step tried again nor a later plan leaves one twice), and triage takes each once with `for update skip locked` under a lease, woken by `NOTIFY`, with a limit on attempts. **The line** (`apps/factory/src/line`, run by `factory line serve` with `LINE_MODE` set to `live` or `dry-run`; `off`, the default, takes no work): a table of the work items on it, by stage and under a lease (`line`), takes the oldest open ticket of the highest severity into Plan when nothing is in Plan or waiting for Build, and runs one step at a time in each of Plan, Build and Review. With `LINE_ONLY` set to a work item, it acts on that one alone: it takes its ticket onto the line whatever else is in Plan or Build, and starts no step for any other work item, reads nothing for it and appends nothing. With `LINE_TAKE` set to a number, it takes tickets by its own rule until it has taken that many work items in all, counted from the `line` table so that a restart takes none more, and then takes no more while it carries those on it to their end. What a work item does next is a pure function of its events (`line/machine.ts`), so after a stop or a crash it carries on from the last event. It opens the ticket's issue through the App as the ticket enters Plan, from the ticket's public view, and the fix's pull request refers to it. Each agent's module (`line/agents/`) says what its step is given, its prompt and schema, and what its result does in GitHub and as events; the worker runs them all one way. A step that hands back nothing, ends out of turns or failing, or hands back a result its agent's schema refuses, runs again as a new job, and after two failures the work item holds for Martin. A coder may instead change nothing and say why, which is no failure: after the gates or a review sent the work back, the work item holds where it came from, under that cause (`gates` or `review`), with the coder's reason; a first round that finds nothing to fix holds as `nothing-to-fix`. A patch the scope fence refuses is recorded as `action.refused` (`scope-fence`, with the fence's output and its verdict on each file), goes back to the coder once, which resumes its session from a fresh checkout, and holds the work item the second time. The coder's first push opens the fix's pull request as a draft, with the ticket's issue and the spec, and it is readied only once the describer has written its description. Each push records its own files and the pull request's whole change, as GitHub compares its head with main. When GitHub or the store fails while a result is acted on, that is not the step's failure: the handback is kept in the `line` table and its effects are tried again later without the agent, each write in GitHub recorded as it is begun and done so that none is done twice, and after six tries the work item holds; failing gates send the work back to the coder twice; a review's blocking findings go back to the coder's session, and a fresh reviewer is told them in the next round, and what still blocks after two reviews holds, as does a review the reviewer escalates, and a work item that has spent its cap on models (the gateway's, from the same `FACTORY_PROFILE`) holds before its next step, with the cap on the hold. Every spec tagged `out-of-scope` that the planner wrote under the rule (its criteria name where each comes from), a rewritten one too, holds at Plan for Martin's approval before the coder starts, in every autonomy mode; approving it carries on to Build, and answering sends it back to the planner. A spec written again once there is a pull request sends the work back to the coder, held to the new one, and sets aside the review of the old one, so the change is reviewed again. Each hold names its cause, and Martin's answer does what `ANSWERS` in `machine.ts` says for that cause: rejecting closes the work item and its issue, an answer runs the step it was held at again or sends the work back to the coder with his words, an answer to the scope fence's hold sends the work item back to the planner with what the fence printed, an answer to `nothing-to-fix` sends it back to the planner with the coder's reason and approving it closes the work item, and approving a held review stands in for the reviewer's. Each step's calls become one `model.called`, summed from `model_calls` by the step's job, with the turns it was given; it counts only the calls a model answered, a cassette replayed, or that failed part way with tokens to show for it, and none the gateway or the provider refused. Each agent's turns and deadline are set for Claude; when `policy/models.ts` sends an agent's calls to the local model (the profile's, under `ALL_LOCAL`, which the line reads as the gateway does), its step has twice the turns and four times as long. `factory line soak-check` reads the store and the cluster the morning after a soak: leases held past their expiry, runners' Jobs and volumes left for ended work items, events that are not valid once upcast, the spend (each work item's within the profile's cap on one, or nothing at all with `--no-spend`, for a night on the local model), and the work items taken, by how each ended, with their minutes in each stage (`line/soak.ts`). Once a minute it reads its pull requests' check runs and merges through the GitHub worker and appends `gates.started`, `gate.finished`, `gates.finished` and `pull-request.merged`, leaving out the factory's own check runs; a pull request closed unmerged closes its work item, and a work item that ends has its runners' volume deleted. Every worker checks for `line.stopped` before it takes work; `make stop-the-line` appends it, and the line deletes the Jobs of every step in hand at once, starts none still preparing, records nothing of them, and runs them afresh when the line starts. A cap the gateway has set and not cleared (`spend.capped`: the factory's own day or month cap, or the provider an agent's calls go to refusing) starts no step for that agent, since every call would be refused; a step that hands back an error while such a cap is set, or after one was set while it ran, counts for nothing and runs again once the cap clears, and the `spend.cleared` that clears it wakes the line (`line/caps.ts`) | Temporal, AWS Step Functions |
| **Event store** | Append-only record of every step, with captured artifacts (spec 5.1) | One Postgres table (`packages/store`), with numbered migrations that a hook Job applies before the console starts. A trigger refuses every update, delete and truncate; appends commit in `seq` order and notify listeners. An event appended again with the same `id` and content is stored once, so a worker can retry; the same `id` with different content is refused. The store records once whether it holds samples or real events, and numbers real work items from 1000. Two roles: the factory's writer appends and reads, the console's reader sees public views only. Event types, their Zod schemas, public views and upcasters are `packages/events`. Artifacts are files named by the SHA-256 of their contents (local disk on a volume; Spaces or S3 by profile) | Snapshots or paged history, if the event count grows |
| **LLM gateway** | Credentials, budgets, logging, redaction, model routing; live, record and replay modes (spec 7.1) | `apps/factory/src/gateway`: a TypeScript service in the `factory` namespace, run by `factory gateway`, the only pod with a model provider's key. **Judgements:** `POST /v1/judgements` takes an agent, a work item, a question set, a pinned model, the state and the questions, and returns the answers with their cost and cassette key; it holds the TypeSafe key, calls Jev with `fetch` (a timeout; retries with backoff, honouring `Retry-After`) and checks every response with Zod. **Agents:** `POST /v1/messages`, Anthropic's Messages API with streaming, for runners (`gateway/agents.ts`). A job token (`packages/store`, `job_tokens`, kept as a hash) stands where the API key would be and names the work item and agent; the gateway refuses it once its job has ended, and every agent call while the line is stopped. The provider, pinned model and, for Claude, effort come from `policy/models.ts`, whatever the runner asked; the local model is sent no effort, since LM Studio reads none from a request: its Reasoning Effort setting for the model decides; prompt caching passes through untouched. Only the request fields, betas and tools the Agent SDK sends get through (`REQUEST`, `BETAS`): a server tool, such as web search, would be a way past the runners' fence, and is refused. Providers: Anthropic, with the key from the Keychain, and LM Studio on `local`, which speaks the same API and costs nothing (`ALL_LOCAL=true` sends every agent there), and is sent the system messages the Agent SDK puts among a step's turns as reminders in the user's turn where each stood, so that each call's prompt extends the last and LM Studio's cache holds; errors go back in Anthropic's shape. A provider refusing because the account's credit is spent or the workspace's limit is reached (read by type and status, by message only where nothing else tells them apart), or the local model not listening, is a cap the factory does not own: no retry, `spend.capped` naming the provider, agent calls answered 429 until a probe a few minutes apart is answered and `spend.cleared` follows. It never logs a state, a prompt or a provider's body. Modes are live, record, replay and replay-record; without a provider's key it replays that provider only. A judgement's cassette is named by the SHA-256 of the provider, model, questions and state; an agent call's by the provider and the request without its metadata, the date in its prompt and the times its tools printed (Vitest's and Biome's, and `ls -l`'s), with the results of tools run at once in the order of their ids, so a step run again replays up to its first changed call. One cap across every provider (`policy/spend.ts`) is counted from the `model_calls` table, the audit log of every call with its tokens, cache reads and writes, cost and job: at a day or month cap the gateway refuses and appends `spend.capped` to the line, and `spend.cleared` when the window ends; each work item has a cap of its own. Prices include the cache's (`gateway/prices.ts`). Metrics for calls, spend and latency over OpenTelemetry | Bedrock on `aws` (milestone 11); LiteLLM behind the same interface |
| **Agent runners** | One disposable sandbox per step, with the repository checked out and its toolchain (ADR 0008) | Two Kubernetes Jobs per attempt at a step in `runners` (`apps/factory/src/runners/jobs.ts`), named by the agent, the work item, the agent's round and how many steps the work item has started (`reviewer-1002-1-4` is the reviewer's first round and the work item's fourth step), so a step tried again never meets the Jobs or the token of the attempt before it, on a volume that lives as long as the work item (`DELETE /v1/work-items/<id>` on the line ends it), under the restricted Pod Security Standard, with no service account token, a read-only root and a deadline. Both run the `factory-runner` image (`apps/runner`: Node, git, pnpm through corepack, the Agent SDK). The prepare pod (`runner prepare`) checks out the commit and installs it (with, for a step that reads a change, its base beside it as the branch `base` and the commits between, so `git log base..HEAD` holds every round's), with no lifecycle scripts, and commits a seed, when the step has one, and a dry run's commits, which GitHub never had, on the real commit under them, as the pull request's own; the seed under a neutral message at a fixed time, so its base has the same sha every run, and gives the checkout's files that time, so a search lists them alike; it may reach the internet on 443. The agent pod (`runner agent`) reaches only the gateway and the line's handback, and has no DNS (the line writes their addresses into its hosts): it checks its own fence, runs the agent on the Agent SDK (Claude Code) with the step's turn limit, no settings from the checkout and a system prompt that is the same on every run, and, for a step that names a skill, that skill alone from the runner's own plugin (`apps/runner/plugin`, read-only in the image; nothing in the checkout or the volume adds one), and hands back a patch of everything changed since the step's commit, committed or not, its note, its turns and its session, and, when the step asks for one, its result: JSON the agent writes to `$WORK/out/result.json`, outside the checkout, with any field the step has it write as a Markdown file of its own beside it read in, up to 64 KiB, each file measured before it is read, which the line reads through that agent's schema (`line/agents/`). A job token, made for the step and ended when it is over, is its only credential. The line (`factory line serve`) starts the Jobs with a service account that may create Jobs and volumes in `runners` and nothing else, takes handbacks at `POST /v1/handback` (checked with Zod; a token, once), and fences each patch to the spec's scope (`runners/scope.ts`), never `.github/`, `deploy/` or a path the app's CODEOWNERS gives a person at the step's commit, which it reads through the GitHub worker. The GitHub worker applies an accepted patch outside the sandbox (`github/patches.ts`). `POST /v1/smoke` on the line's port-forwarded API runs a coder on an off-by-one seeded in a scratch copy of the app, with the GitHub worker in a dry run. `factory line bench <agent> <fixture>` runs one agent's step on a developer's machine, with the runner's own two steps and no network fence, on a fixture of invented work (`line/bench/fixtures.ts`), against a gateway on the host, and fences a coder's patch as the line does, sending one it refuses back, and commits a reviewer's change on the base as the pull request's head: in a fixed folder in the developer's own cache, with a home emptied each run and none of the developer's environment but `PATH`, so a second run replays from the cassettes; each run, and each smoke run, caps its spend as a work item of its own | gVisor or Firecracker isolation |
| **Factory GitHub App** | The factory's identity in GitHub | `mrogan-software-factory`, on Martin's account and installed on the two public repositories; its work shows as `mrogan-software-factory[bot]`. Permissions below. No webhook: the factory polls | |
| **GitHub worker** | The only pod with the App's key, and so the only thing that acts in GitHub as the factory | `apps/factory/src/github`, run by `factory github run`. It signs a JSON Web Token with the key (the Client ID as issuer) and trades it for an installation token narrowed to one repository, made when needed and an hour long; neither is ever logged. Its actions (`github/actions.ts`): branches, signed commits through GraphQL's `createCommitOnBranch` (never `git push`), opening, updating, labelling and readying pull requests, updating a branch, comment reviews anchored to lines, check runs, issues and comments. The other workers ask for them over HTTP, `POST /v1/actions/<action>`, each body checked with Zod and naming one of its repositories. It moves, deletes and commits to the factory's own branches only, and refuses any other before GitHub is asked (`github/branches.ts`): those under `factory/` (a fix is `factory/<work item>-<a few words of its ticket's title>`) and the deploy branches. The line reads through it too, `POST /v1/reads/<read>` (`github/reads.ts`): a pull request's state, the check runs on a commit, the checks a branch's rulesets require, a branch's head, and how a commit compares with a branch (its merge base, and each file it changes with its patch), each a conditional request, and the paths no patch may change at a commit (the workflows, the deployment and what its CODEOWNERS gives a person); the worker itself touches no store. The other workers' calls must be JSON, and on a host it listens on loopback only. Every answer from GitHub and GHCR is read through a Zod schema. A request is retried after a rate limit, and after a timeout or server error only if repeating it is harmless (never a POST). A poller runs watches once a minute with conditional requests, so an unchanged answer costs nothing against the rate limit; it offers watches for the check runs on a commit, merges, and new image tags in GHCR (read through the registry's API, anonymously). Each change goes to whatever waits for it, and one a handler failed on is handed over again, without holding back the rest. Watches act on what they see, in both repositories. **Deploys** (`github/deploys.ts`): when main has a newer commit that every image of a pin file was built from, the App commits the new digests on main's head, through a scratch branch under `factory/`, moves that file's deploy branch to the commit in one forced update, and opens its pull request, labelled with the profile and linking the changes since the commit pinned now, or retitles the one open for an older build (the branch is never at main's head, where GitHub would close that pull request for having nothing to merge); one open deploy pull request per pin file, and a build whose pull request was closed unmerged is not proposed again. When main moves on with no newer build, the commit is made again on main's new head the same way, unless Martin has approved the pull request; the deploy branch has this one writer. A pass reads everything at one head of main. **Releases** (`github/releases.ts`): each time main moves, release-please, run as a library with the App's token, tags and publishes a merged release and keeps the release pull request current. A third keeps the App's pull requests current (`github/current.ts`): one that has fallen behind main and that nobody has approved is updated, since an update after approval would make the approval stale (ADR 0009); a deploy pull request is left to the deploy watch. None runs without the key, and releases do not run in a dry run. With no key it reads and writes nothing, and says so; with `GITHUB_DRY_RUN`, or for a worker that asks with `x-factory-dry-run` (the line in `dry-run`, the smoke run), it writes each action it would have taken to the artifact store instead, with the files a commit would have held. A dry run's reads answer for what it would have made (`github/dry-run-reads.ts`), from its memory, which lasts as long as the worker: its pull request is open, its head the last commit it would have pushed; each commit it made has every check main's ruleset requires, passing `GITHUB_DRY_RUN_CHECKS_SECONDS` after it (120 by default), each titled as having run nothing; a comparison is taken from the real commit its first commit went on; a step that starts from one of its commits is told the real commit under it and the dry run's commits as patches (`checkout`), which the runner's prepare step makes on it, so the reviewer, the describer and a later round see the change; and the pull request is merged, as the App, `GITHUB_DRY_RUN_MERGE_SECONDS` after it is readied (1200), never while it is a draft, so a line in `dry-run` goes round. Everything else it reads from GitHub. `factory github workflow-refusal` has the App try to add a workflow, after a control commit GitHub must accept, and keeps GitHub's refusal (`apps/factory/test/github/workflow-refusals.json`) | |
| **Scoreboard** | Matches tickets to answer-key fingerprints | Separate service; the only component that can read the answer key | |
| **Defect injector** | Opens regression PRs from the private catalogue | Job triggered by Martin, schedule or visitor menu | |
| **Red-team harness** | Runs curated attacks against real mechanisms and records the refusals | Job that launches an adversarial agent or scripted action per attack | |
| **Console** | The UI for visitors and admin (spec 5) | React 19 single-page app built by Vite 8 (ADR 0007) in its own image stage. The Node server serves the build by Vite's manifest, the public events as JSON and as server-sent events resuming from `Last-Event-ID`, and the artifacts public events refer to. The browser projects: `project(events, t)` is plain TypeScript, so live and replay are the same code; the same build, fed from an event-log folder, is the replay site. The image holds neither the factory's code nor the app's repository: what the projection shares with the line (its limits, how a scope matches a path, a return's words) is in `@software-factory/events`, which both read, and a spend hold carries its cap; the app's reviewing rules are the one copy it keeps | |
| **Workers and images** | Where the gateway, the GitHub worker, triage, the intake, the log watcher, the line, the probes and the crawler run | One Deployment each in `factory` (`deploy/base/factory`), one replica, writing to the event store as the factory's writer and to the artifacts volume (which the console still mounts read-only). Three images, built by `build.yml` and pinned by digest per profile in a pull request the App opens (ADR 0005): `factory`, distroless Node, for the gateway, the GitHub worker, triage, the intake, the log watcher and the line; `factory-browser`, from the pinned Playwright image, running as an unprivileged user, for the probes and the crawler; and `factory-runner`, for the runners' Jobs, whose pinned reference the line is given as `RUNNER_IMAGE`. Chromium runs without its own sandbox, which the restricted Pod Security Standard refuses it, so the pod's other fences carry that. The gateway's cassettes are on a volume only it mounts, so recordings of real reports stay in the cluster. `make up` creates its Secret from `TYPESAFE_API_KEY` or the Keychain, through stdin and no file; with none it replays only. It creates the GitHub worker's from the Keychain's `factory-github-app-key` the same way; with none, that worker reads and writes nothing | Spaces or S3 for artifacts, a cloud secret store for the key |
| **Network policies** | Only the gateway and the GitHub worker may leave the cluster | In `factory`, everything is denied in and out, then each pod is allowed what it needs: DNS, Postgres and the collector for the workers; Prometheus, Loki and Tempo for the intake and log watcher; the app for the probes and crawler; the gateway for triage; Alertmanager for the intake. The gateway and the GitHub worker alone may reach the internet, on port 443, outside the cluster's own and the local network's addresses; only the line may call the GitHub worker. k3s enforces them. `make egress` starts a pod labelled like a worker and shows it reaches nothing, while the gateway reaches TypeSafe and the GitHub worker reaches GitHub and GHCR | |
| **Factory command** | `factory events load`, `play` and `export`, `factory probes`, `factory crawler`, `factory github`, `factory gate` and `factory line` (spec 5.6 names the command) | `apps/factory`: moves event-log folders in and out of the store, refusing to mix samples with real events; its capture step (Playwright: a screenshot and where the probe looked) is how the probes keep evidence; `factory probes run` runs the probes, and `factory probes once` prints what each check finds without writing to the inbox | Keys, and the workers' entry points |
| **Samples** | What the console shows in development and in its tests, where there is no real work | Nineteen hand-written work items (`packages/samples`), typed against the events, the last seven fixes as the line makes them (rounds of review, a wait for Martin's merge, each kind of hold, a merge waiting for a release, a run on the local model), with real screenshots of the app with each sample's change made in a scratch copy; exported as an event log that `make check` keeps current, and checked against the answer key in the private repository. The cluster's store holds real events (`make real-store`) | |
| **Visitor access** | Keys, usage tracking, rate limits, visitor budget (spec 5.6) | Part of the console backend; keys in Postgres | |

### Factory GitHub App permissions

- **Allowed:** contents (branches), pull requests, checks, issues.
- **Denied:** workflows, administration, bypassing rulesets.

## Agents

| Agent | Reads | Produces | Constraints |
|---|---|---|---|
| **Triage** | Probe, crawler, telemetry and canary signals; user reports; the planner's findings | Deduplicated, classified tickets with evidence | `packages/triage`, run by `factory triage`. A sense's signal takes its category and severity from `policy/triage.ts` and repeats by fingerprint; only reports and the planner's findings go to Jev (`triage/v1`), with routing as plain code. Quarantines injection attempts; parks suggestions for Martin; one fingerprint, one ticket. A planner's finding is trusted no more than a report, since a visitor can read the app's public code and argue an agent into seeing a bug: it is judged the same way but never opens a ticket (`routeFinding`). A defect it noticed holds for Martin (cause `finding`, with its fingerprint as a report's ticket would have it: the route the planner named and the symptom Jev judged, or for wrong words the passage of the page Jev chose); one that repeats an open ticket joins its evidence, though never the ticket the planner was planning, which it is beyond: one with that ticket's fingerprint is held, saying so, until that ticket closes and a sense's ticket can take it. A ticket triage opens later with the same fingerprint, from a sense or a report, closes the held defect into it ("A sense saw it: ticket #N"). Martin approving it opens its ticket on its own work item, with the category and severity `policy/triage.ts` gives its symptom, as a sense's would be, or joins it to an open ticket that has it; rejecting closes it; an answer in words leaves it waiting. Triage does as he answered once an event is appended, reading only the finding holds (an index of their own), and leaves one it cannot act on after as many tries as a signal gets. Nothing else opens a ticket from a finding |
| **Planner** | Tickets; Martin's improvement requests | A spec per ticket: outcome, acceptance criteria, scope, risk, rollout | `line/agents/planner.ts`, in a runner at the commit the fix starts from, 30 turns and 15 minutes. Its prompt holds the ticket's public view and each sense's signal by its typed fields (`line/agents/evidence.ts`): never a report, and no log message, since an app may log what a visitor typed, quoted or not; a log signal is told by its route, its requests and its lines at each level, and every route is cut at its query. Its result is a spec, a rejection or a question, read with Zod, each with up to five `findings`. Each criterion names what in the ticket's evidence asks for it (`from`: the ticket, a numbered signal, or Martin's answer); one nothing asks for does not belong in the spec. Anything else it notices is a finding (a page, its route and a sentence), which the line leaves in triage's inbox as a signal from the planner, naming the work item it was planning, once for the work item however often it plans; its words are kept from every public view and every agent, as a report's are. A scope is a plain path in the repository and never names `.github/`, `deploy/` or a path the app's CODEOWNERS gives Martin at that commit, which the line reads through the GitHub worker. A result the schema refuses fails the step, and the next attempt is told why. Rejects what it cannot make testable or what only a protected path would fix, and asks Martin what only he can say; both hold the work item. His answer to either reaches every later plan with what he was asked; rejecting closes the work item, and so does approving the planner's rejection |
| **Coder** | Planner spec, the ticket's evidence, the repo and its `AGENTS.md` | Failing test, fix, and a patch with a title and a note | `line/agents/coder.ts`, in a runner at the commit the fix starts from (the pull request's head in a later round), 50 turns and 30 minutes. Its prompt holds the ticket's public view and each sense's signal by its typed fields, as the planner's does (`line/agents/evidence.ts`), and the spec with its scope as the only files it may change; it writes the test first, and leaves alone what else it notices. Its result is a Conventional Commit title and the commit's note, or, when the change needs none, why it changed nothing, in at most 200 characters, read with Zod; a step that hands back no change and does not say why has failed. The line fences its patch to the spec's scope before anything reaches GitHub; it cannot sign, merge or touch workflows |
| **Reviewer** | The ticket's public view and what the senses saw, Martin's answers at Plan, the pull request's diff, the spec and the app's `docs/REVIEWERS.md` at the base, once the gates pass | A comment review, a check run, and its findings | `line/agents/reviewer.ts`, in a runner at the pull request's head with its base beside it, 30 turns and 15 minutes. It reads the rules as they are at the base, so a change cannot loosen them, and holds the coder's claims to the diff. It holds the spec to the ticket, with Martin's answers as part of it, as well as the diff to the spec. A criterion they do not ask for is a blocking finding that cites that criterion and the ticket, and the schema makes such a review an escalation, in every autonomy mode, since the coder cannot put a spec right: it holds as `beyond-ticket`, his answer sends the spec back to the planner, his approval stands in for the reviewer's, and rejecting closes it. A change that goes beyond a sound spec is an ordinary blocking finding citing the spec or a rule, and goes back to the coder. Its result is a verdict (approved, changes requested, or escalated to Martin), a note and up to 20 findings, each anchored to a line, blocking or not, citing a rule's number, a criterion of the spec or the ticket, in at most 300 characters, read with Zod. The line posts it through the GitHub worker as a comment review, with a finding the diff does not show in its body (`line/review.ts`), and the check run `factory review`, which no ruleset requires: a signal, never a gate. The check run is made first and the review second, each once for a handback, so GitHub failing between them never runs the reviewer again. Blocking findings go back to the coder's session; after two reviews, what still blocks holds for Martin, as does an escalation, and his answer sends the work round again, his approval stands in for the reviewer's, and rejecting closes it. `factory reviews rules` counts findings by rule from the event store, so a rule never cited can go and one cited often can become a lint rule or move into `AGENTS.md` |
| **Describer** | Once review approves: the ticket's public view and what the senses saw, the spec, the final diff and the coder's commit messages, the review thread round by round | The pull request's title and description; the work item's summary (`work-item.summarised`) | `line/agents/describer.ts`, in a runner at the pull request's head with its base beside it, with a fresh context, 30 turns and 15 minutes. It names the runner's `visual-pr` skill (vendored from HumanLayer under MIT, `apps/runner/plugin`), which fits a description to its change, a line if a line will do, and reads the repository's pull request template as questions to answer, not headings to fill. It writes the description as a Markdown file beside its result; the title is a Conventional Commit of 80 characters at most, and the summary is a title, two lines for the card and the paragraph at the top of the sheet, all read with Zod. The squash commit takes the description as its message, so the schema refuses a closing keyword before an issue, which would close the ticket's issue on merge rather than once the fix is verified, and an @mention outside code; a refused result runs the step again, told why. The line sets the pull request's title and description, with the line that refers to the ticket's issue, then takes it out of draft, each once for a handback, and appends the summary; then the work item waits for Martin's merge |

Alertmanager has one receiver, a webhook to the intake. | **Log watcher** | The app's logs, read for what a query cannot say (`factory logs`) | Three checks, each with its own cursor, reading Loki. **New error patterns:** error records reduced to a pattern (numbers, identifiers, hashes, quoted values and the request's own path taken out, the exception the record attaches kept) and signalled by route when the previous day has not shown them, with the lines and trace ids, and the spans when Tempo already has the trace; the evidence names the route that served the error, or the root when none did, never the request's own path. **Reports:** each record of the widget becomes a `report` signal; the text goes to the inbox and to no log line, metric label or error message. **Agreement:** per route, the requests counted in metrics, logged and traced over two windows that ended minutes ago (Tempo answers late); the odd one out is `missing-log` or `wrong-metric`. A sense runner (`apps/factory/src/senses`) runs them every few minutes and at once when `/version` changes, and sends a signal only for a check that has failed twice in a row, with a screenshot and the evidence. A check that costs something, such as sending a contact message, may run at most so often (the contact checks, once an hour). `factory probes run` also serves a page reader for triage (`POST /v1/pages` with a path: a screenshot in the artifact store, and the page's text in passages). The crawler (`apps/factory/src/crawler`, `factory crawler run`) follows every link, image, script and stylesheet from the home page on the same origin, up to a cap, and checks each page and asset: broken links and images, redirect loops, server errors, console errors, accessibility with axe (only the rules that name a class: missing alt text, contrast, unlabelled fields), the usual security headers, caching of static assets, response time, and whether the error pages for a missing page and a malformed request give away stack traces, paths or software versions. It uses the same runner, so a check signals after failing twice in a row. A finding is on the route template worked out from the URLs it saw (`/products/:slug`), and a class found on every page crawled is one finding for `*`. A page is opened only at its own address: a link that redirects is judged on the route asked for for what is about the request (a redirect loop, a server error, a slow answer), and where it lands is crawled as a page of its own, so what is wrong with that page is on its route. What only an opened page can show (its headers, console, accessibility, and the links and images it holds) is checked where a page was opened, and is trouble, not a pass, on a route whose link led to no page (a loop, an error status, a page that would not open). Each probe is tested against a small shop made in the test, with and without its fault; those tests run in the pinned Playwright image | |
| **The app** | The World's Worst Website (spec 3) | TypeScript on Node, pages rendered on the server, no framework. Catalogue in SQLite (`node:sqlite`), built into the image and read-only. Baseline and canary side by side, each with its own data | |

## Guardrails and what enforces them

The guardrails are defined in spec section 6. This table shows which component holds each one.

| # | Guardrail | Enforced by |
|---|---|---|
| 1 | Agents cannot change the rules | GitHub App has no workflows permission; rulesets and CODEOWNERS |
| 2 | Gates are deterministic | Required checks on the ruleset; reviewer agent is a non-required check |
| 3 | Only the pipeline builds releasable artifacts | cosign signing via OIDC; Kyverno admission control (also a red-team attack) |
| 4 | No agent writes to production | Argo CD pulls from git; runners have no cluster credentials; telemetry access is read-only |
| 5 | Sandboxes are disposable and fenced | Kubernetes Jobs; NetworkPolicy egress allowlist; no secrets mounted |
| 6 | One gateway for all model access | Only the gateway holds model credentials |
| 7 | Hard spend caps | Gateway budgets per day, month, task and visitor, across every provider |
| 8 | Inputs are untrusted | Typed Jev answers in triage; gates, scope fences and approval routing, not prompts |
| 9 | Everything is reversible | Argo Rollouts; orchestrator stop-the-line switch |
| 10 | Public means hostile | Factory acts only on its own or Martin-labelled issues; `pull_request` only; GitHub-hosted runners |
